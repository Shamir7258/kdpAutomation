- [x] **Found and fixed a significant pre-existing bug, platform-wide, not specific to this phase**: every job-enqueuing service (`content.service.ts`, `editing.service.ts`, `interior.service.ts`, and the new `cover.service.ts`) called `queue.add(data)` *then* `jobService.createPending(...)` to create the tracking `Job` Mongo doc — a race condition where, if the worker picks up and finishes the job before that Mongo write lands (which the mock providers are fast enough to do reliably, especially for cover/interior generation), the worker's `JobModel.findOne({ bullJobId: job.id })` lookup finds nothing, silently skips both `markRunning`/`markCompleted`, and the job stays stuck showing `"pending"` forever — even though the actual work (the `Interior`/`Cover`/`ContentVersion`/`EditPass` document) was created successfully. This is why interior/cover generation appeared to hang indefinitely in the Playwright walkthrough despite the files existing in storage the whole time: the frontend's completion-watching `useEffect` (the same pattern fixed for `EditPassesPanel` in Phase 5) was correctly watching for the job to reach `'completed'`, but that status update was the thing silently getting dropped. Applied identically to all four services. This also explains (and fixed) the "occasionally flaky under host contention" note on `content-generation.integration.test.ts` since Phase 4 — it was very likely hitting this exact race under load, not a host-contention artifact as originally diagnosed; the diagnosis was reasonable given the evidence available at the time (the flake really did correlate with system load, which also affects race-window timing), but the actual root cause was this ordering bug.

## Notes / follow-ups
- Frontend has no component/unit tests yet (`npm run test -w @kdp/frontend`
  passes via `--passWithNoTests` — it was failing the root `npm test`
  before this fix, since vitest exits non-zero with zero test files).

  browser walkthroughs instead (see Phase 1/2 notes above). Add real

  larger and regressions become harder to catch by hand.

  multi-instance deployment (see ARCHITECTURE.md §5).
- MongoDB Atlas Search integration (§7 research, in-app content search)
  deferred until Phase 3 (Research) and a real Atlas cluster is available;
  local dev falls back to basic Mongo query filters behind the same
  search-layer interface so swapping in Atlas Search / Elasticsearch later
  doesn't change callers.
- Idea generation is synchronous (no BullMQ job) — fine for a handful of
  ideas per call, but should move onto the Phase 4 job queue once content
  generation (which is genuinely long-running) introduces BullMQ, for
  consistency.
- `packages/ai` pins `@anthropic-ai/sdk@^0.117.1` and `openai@^6.49.0` —
  both far newer than what training-data intuition would guess; verified
  against the live npm registry rather than assumed. `openai@7.x` requires
  Node 22 (this repo targets Node 20), which is why it's pinned to `6.x`.
- This dev session's local `apps/backend/.env` points `REDIS_URL` at a
  non-default port — ports 6379 and 6380 were both already occupied by
  unrelated pre-existing services on this particular sandbox machine.
  `.env` is gitignored, so this is a local-only override; `docker-compose.dev.yml`
  (and `.env.example`) still correctly default to the standard `6379`.
